1. Executive Summary

During routine operational threat monitoring within the Splunk SOC laboratory network, an automated alert detected abnormal authentication volume against the monitored Linux endpoint ubuntu-p3 (192.168.100.9). An adversary located at internal IP 192.168.100.7 initiated an automated credential guessing and password spray campaign over SSH (TCP 22).

Key Incident Finding: A total of 13 authentication failures were generated within a 3-minute window (00:13:12 to 00:16:15). Forensic analysis isolated a dual-vector attack: a horizontal password spray probing 8 distinct usernames (admin, root, guest, test, user1, user2, service, backup) and a targeted brute-force burst focusing on privileged account admin (4 attempts). Legitimate administrative access was confirmed for user natto from host 192.168.100.1. No breach occurred.

3. Telemetry Ingestion & Field Normalization

The Splunk Universal Forwarder on ubuntu-p3 continuously monitors /var/log/auth.log, transporting raw authentication strings to index=linux_security under sourcetype linux_secure. Because raw logs contain unindexed variables, a normalized SPL regular expression was validated to extract standard security entities:

index=linux_security sourcetype=linux_secure ("Failed password" OR "Accepted") | rex "Failed password for (invalid user )?(?<username>\S+) from (?<src_ip>\d{1,3}(?:\.\d{1,3}){3})" | rex "Accepted \S+ for (?<username>\S+) from (?<src_ip>\d{1,3}(?:\.\d{1,3}){3})" | eval auth_status=if(match(_raw, "Accepted"), "SUCCESS", "FAILURE") | table _time host src_ip username auth_status _raw | sort - _time

6. Production SPL Detection Query Library

Five specialized SPL queries were engineered and empirically verified against the live lab dataset:

  • High-Volume Failure Velocity (5-min window):
    index=linux_security sourcetype=linux_secure "Failed password" | rex "Failed password for (invalid user )?(?<username>\S+) from (?<src_ip>\d{1,3}(?:\.\d{1,3}){3})" | bin _time span=5m | stats count as failures dc(username) as targets by _time, src_ip, host | where failures >= 5 | sort - failures
  • Horizontal Password Spray Detector:
    index=linux_security sourcetype=linux_secure "Failed password" | rex "Failed password for (invalid user )?(?<username>\S+) from (?<src_ip>\d{1,3}(?:\.\d{1,3}){3})" | stats count as total_failures dc(username) as unique_targets values(username) as targets by src_ip | eval attack_type = if(unique_targets >= 3, "Horizontal Password Spray", "Targeted Brute-Force") | table src_ip attack_type total_failures unique_targets targets | sort - total_failures
  • Failed-to-Success Outcome Correlation:
    index=linux_security sourcetype=linux_secure ("Failed password" OR "Accepted") | rex "Failed password for (invalid user )?(?<username>\S+) from (?<src_ip>\d{1,3}(?:\.\d{1,3}){3})" | rex "Accepted \S+ for (?<username>\S+) from (?<src_ip>\d{1,3}(?:\.\d{1,3}){3})" | eval is_fail=if(match(_raw, "Failed password"), 1, 0), is_succ=if(match(_raw, "Accepted"), 1, 0) | stats sum(is_fail) as failures, sum(is_succ) as successes by src_ip, username | eval alert_severity=case(failures >= 3 AND successes >= 1, "CRITICAL: Potential Account Breach", failures >= 5, "HIGH: Active Brute-Force", true(), "LOW") | table alert_severity src_ip username failures successes | sort - failures

8. Incident Remediation & Defensive Hardening

  1. Host-Level Automatic Banning (fail2ban): Deploy fail2ban on ubuntu-p3 to temporarily drop source IPs exceeding 5 failed login attempts in 10 minutes:
    sudo apt-get install -y fail2ban sudo systemctl enable --now fail2ban
  2. Enforce Key-Based Authentication: Disallow password authentication in /etc/ssh/sshd_config:
    PasswordAuthentication no PubkeyAuthentication yes
  3. UFW Network Filtering: Restrict SSH management access exclusively to authorized jump-host IP 192.168.100.1:
    sudo ufw allow from 192.168.100.1 to any port 22 proto tcp sudo ufw deny 22/tcp
